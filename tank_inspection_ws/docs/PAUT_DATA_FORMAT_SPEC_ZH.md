# 超声相控阵（PAUT）数据格式规格 v1.0

- **文档日期**：2026-09-11
- **状态**：拟定，待设备端与采集端双方确认
- **依据**：厂商《相控阵数据格式》表（`docs/image.png`）；行业规范 ONDE / UFF / DICONDE（对照见 `docs/PAUT_DATA_STORAGE_FORMATS_ZH.md`）
- **适用**：设备端 → 采集主机 的 UDP 线格式；同时作为落盘（MCAP / HDF5）字段契约

---

## 1. 设计原则

| # | 原则 | 理由 |
|---|---|---|
| P1 | **元数据随帧传输，每包自描述** | UDP 无连接、会丢包、设备会重启。采集头仅约 80 B，相对负载可忽略（见 §8），换来「任意一包可独立解析」 |
| P2 | **不缩放、不归一化、不滤波** | 保真。缩放因子写入元数据，由消费端决定如何用 |
| P3 | **字段名内嵌单位** | 厂商原用 mm/°/ns/m/s 混用。保留原单位避免精度损失，但字段名必须自带单位后缀 |
| P4 | **显式声明维度与类型** | 不靠约定推导。`sample_dtype` / `beam_count` / `element_total` 全部显式 |
| P5 | **长度字段可扩展** | `header_len` 允许追加字段而不破坏旧消费端（ONDE 用 JSON 达成的效果，这里用长度字段低成本实现） |
| P6 | **区分「未知」与「零」** | 未标定/未连接时写 `NaN` 或专用枚举，**不得写 0** |
| P7 | **小端字节序** | 显式声明，不依赖主机字节序 |

**⚠️ P7 是修复项**：现有实现按主机字节序 `memcpy`（`paut_udp_receiver.cpp:118`），大小端异构时会静默出错。

## 2. 报文体结构

```
┌──────────────────────────────────┐
│ A. 包封装 Packet Envelope   20 B │  魔数 / 版本 / 长度 / 校验
├──────────────────────────────────┤
│ B. 采集头 Acquisition Header 80 B│  板卡 + 探头 + 模块 + 扫查 + 保留 + 时间基准 + 位置基准
├──────────────────────────────────┤
│ C. 帧块   Frame Block       40 B │  帧号 / 设备时戳 / 编码器 / 维度 / 状态 / 分片
├──────────────────────────────────┤
│ D. 数据段 Payload          N B   │  原始数据数组
├──────────────────────────────────┤
│ E. 饱和掩码 Saturation Mask 可选  │  每样本 1 bit（见 §7）
└──────────────────────────────────┘
```

> 采集头**每帧都发**（P1）。80 B ÷ 20 KB ≈ 0.4%，代价可忽略。

### 4.6 时间基准（偏移 63–72，10 B）★ 新增

> 行业对照：UFF `sampling_frequency` + `initial_time`；ONDE `Ultrasound` 轴的 `resolution` + `offset`
> **本段是原表最大的缺口**——没有它，167 个采样点无法换算成深度。

| 偏移 | 长度 | 字段 | 类型 | 单位 | 说明 |
|---|---|---|---|---|---|
| 63 | 4 | `sampling_rate_hz` | f32 | Hz | ADC 采样率。未知写 `NaN` |
| 67 | 4 | `initial_time_us` | f32 | μs | **下标 0 对应的声程延时**。未知写 `NaN` |
| 71 | 1 | `adc_bits` | u8 | bit | `0`=未知；如 `16` |

> 行业对照：ONDE `UCoordinate`/`VCoordinate` 的 `resolution` + `offset`

| 枚举 | 取值 |
|---|---|
| `board_type` | `0`=多浦乐 `1`=中科 `2`=奥斯迪康 |

### 5.1 `status_flags` 位定义

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `has_data` | 本帧数据有效 |
| 1 | `saturated` | 本帧存在饱和样本 |
| 2 | `no_sync` | 编码器/触发失同步 |
| 3 | `encoder_valid` | 编码器值有效 |
| 4 | `is_fragmented` | 本帧被分片（配合 `frag_index/count`） |
| 5 | `calibrated` | 标定参数齐备（`sampling_rate`/`velocity` 等非 NaN） |
| 6–15 | 保留 | 填 0 |

> 行业对照：ONDE `AScanStatus`（`hasData`/`saturated`/`noSynchro`）。
> **原表完全没有状态位**，这是设备端需要新增的唯一功能性字段（见 §9 决策 D1）。

## 6. D. 数据段（Payload）

**布局由 `scan_mode` 决定**（与原表一致），元素类型由 `sample_dtype` 决定。

| `scan_mode` | 结构 | 元素数 | 说明 |
|---|---|---|---|
| `0` 线扫 / `1` 扇扫 | `[波束个数][采样点数]` | `beam_count × sample_count` | 行优先，**波束为外层轴** |
| `2` 全聚焦 | `[发射阵元][接收阵元][采样点数]` | `element_total² × sample_count` | ⚠️ 见 §6.1 |
| `3` TOFD | 待定 | — | 需设备方补充 |
| `4` PWI | 待定 | — | 需设备方补充 |

**轴序必须显式约定**（P4）。线扫/扇扫按原表 `[波束个数][采样点数]`，即**同一波束的全部采样点连续存放**——这是最自然的 A 扫布局，消费端 `reshape(beam_count, sample_count)` 即可直接用。

> **与 v0 的差异**：v0 实测为 `[采样点数][波束]`（转置）且无声明，是静默错位风险源；v1 统一为 `[波束][采样点数]`。

### 6.1 全聚焦（FMC）三处待确认

1. **原表只写了 `[阵元总数] × [阵元总数]`，未提采样点数。** FMC 的每条收发对都有完整 A 扫，实际应为 `[阵元总数][阵元总数][采样点数]`。**请设备方确认这个三元结构。**
2. **收发轴序**：`[发射][接收]` 还是 `[接收][发射]`？行业惯例（FMC）为 `[发射][接收][采样]`，建议采用。
3. **分片**：32 阵元 × 32 × 167 × 2 B ≈ **342 KB/帧**，**远超 UDP 单包上限 65,507 B**，必须分片。见 §8。

### 6.2 元素类型 ★ 建议改为 u16

原表规定 `原始数据数组(ushort)`，即 **u16**。但现有线格式实测为 **i32**（`paut_udp_receiver.cpp:124` 按 `8 + h*w*4` 校验且通过）。

**改为 u16 的理由**：

| 收益 | 说明 |
|---|---|
| 带宽减半 | 40,748 B → 20,374 B/帧 |
| 类型一致 | 与厂商规格一致 |
| **可能找回动态范围** | 现有实测值域仅 `0–255`，而 u16 可表达 `0–65535`。若 ADC 实为 16 位，**当前可能只传了低 8 位** |

> ⚠️ **仅改类型不够**。若设备内部确实在 8 位处截断，改 u16 传输不会自动恢复丢失的高位——**需同时修正设备端的缩放/截断逻辑**。这是本次改动中**潜在收益最大**的一项（缺陷检出率直接相关）。

## 7. E. 饱和掩码（可选段）

由 `status_flags.saturated` 指示是否附送。

| 项 | 说明 |
|---|---|
| 位置 | 数据段之后，包尾 |
| 长度 | `ceil(元素数 / 8)` 字节 |
| 编码 | 每样本 1 bit，`1` = 饱和；按数据段同一轴序排列 |
| 开销 | 线扫 `ceil(10187/8)` ≈ **1,274 B**，占 u16 数据段（20,374 B）的 **6.3%** |

> 行业对照：ONDE 只有整帧级 `AScanStatus`；逐样本掩码是其超集。
> **优先级**：`saturated_count`（帧块，必做）→ 逐样本掩码（可选）。若设备端算力允许，建议做——**没有它，饱和样本只能靠 `value == max` 硬判，而恰好等于 max 的有效回波会被误杀**。

## 8. 带宽与分片

| 模式 | 每帧负载 | @43.5 Hz | 可行性 |
|---|---|---|---|
| 线扫 · i32（现状） | 40,748 B | 1.77 MB/s ≈ **14 Mbit/s** | WiFi 可承受 |
| 线扫 · u16（建议） | 20,374 B | 0.89 MB/s ≈ **7 Mbit/s** | 宽裕 |
| 全聚焦 · u16 | **342,016 B** | **14.9 MB/s ≈ 119 Mbit/s** | ⚠️ **WiFi 不可行** |

### 8.1 全聚焦模式的两条硬约束

1. **必须分片**：342 KB 远超 UDP 单包 65,507 B。需按 §5 的 `frag_index/frag_count` 分片重组。
   - 分片大小建议 ≤ 60,000 B（留出封装余量）→ 每帧约 6 片
   - **任一分片丢失 = 整帧作废**，`status_flags.is_fragmented` + `frame_seq` 用于识别
2. **带宽需重新评估**：119 Mbit/s 持续吞吐**超出 WiFi 实际能力**。可选方案：
   - 切**有线以太网**（首选）
   - 大幅降低 PRF / 帧率
   - 减小阵元数或采样点数
   - 由设备端在 FMC 模式下自行降采样（但会损失保真，与 P2 冲突，不推荐）

> **建议**：线扫先按 u16 落地并验证，全聚焦作为**第二步**，且必须**先确定物理链路**再定协议。

## 10. 验收清单

协议落地后，按序验证：

| ID | 验证项 | 方法 | 通过标准 |
|---|---|---|---|
| V1 | 报文完整性 | 检查 `magic` / `version` / `crc32` | 丢包计数为 0，CRC 全通过 |
| V2 | 维度自洽 | `packet_len == 20 + header_len + 40 + 元素数 × sizeof(dtype)` | 逐包相等 |
| V3 | **采样率正确性** | 量已知厚度试块，底波落在第 N 点，反算 `fs` 与 `2×深度/声速/N` 对比 | 误差 < 2% |
| V4 | **动态范围** | 观察样本值域 | 若仍恒 ≤255 → D3 未生效，需回查设备端缩放 |
| V5 | 编码器有效性 | 手动移动探头，观察 `scan_axis_encoder` | 单调变化，`encoder_resolution_mm` × Δcount ≈ 实际位移 |
| V6 | 声速正确性 | 用 `specimen_velocity_m_s` 反算深度，与试块实际厚度对比 | 一致 |
| V7 | 轴序正确性 | 探头扫过台阶/缺陷 | 回波**沿采样轴平移**（而非波束轴） |
| V8 | 状态位 | 人为制造饱和 | `saturated_count > 0`，`status_flags.saturated` 置位 |
| V9 | 全聚焦分片（若启用） | 校验重组后帧数与 `frame_seq` 连续性 | 无缺帧，`frag_index` 完整 |

| §5.1 状态位 | `AScanStatus` | —（UFF 无） |

> 落盘为 HDF5 时，本规格的采集头 → ONDE 的 `/Public/Setup`（JSON）；帧块 + 数据段 → `/Public/Groups/<Gid>/Datasets/<Did>-AScanAmplitude`。

## 13. 版本与兼容
