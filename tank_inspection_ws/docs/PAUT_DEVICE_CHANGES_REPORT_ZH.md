# 超声相控阵（PAUT）数据外发改造 —— 阶段汇报

- **日期**：2026-09-18
- **范围**：设备端（C# 上位机）新增 UDP 原始数据外发通道；采集端配套验证工具
- **状态**：✅ 已跑通端到端链路（配置/心跳/数据帧三类包均可达），⚠️ 帧率待调

---

## 一、做了什么

给超声相控阵上位机**新增一条独立的 UDP 外发通道（`12346`）**，把此前从未外发的**元数据 + 完整原始 A 扫**发出来，供机器人侧采集。

**关键点：现有 `:12345` 通道完全未改动**，两条链路互不影响。

| | 现有 `:12345` | 新增 `:12346` |
|---|---|---|
| 数据 | 成像算法裁剪后的 `61×167` int32 | **完整 `61×896` uint8 原始 A 扫** |
| 元数据 | 无 | 板卡/探头/楔块/扫查/时基/编码器 共 39 字段 |
| 线程 | UI 线程定时器 | **独立发送线程**（不阻塞采集） |
| 用途 | 实时成像 | 数据采集 / 训练 |

## 四、线格式（概要）

**全包小端，紧凑排列（无填充字节），消费端必须按显式偏移读取。**

| 包类型 | 值 | 发送时机 | 长度 |
|---|---|---|---|
| `CONFIG` | 1 | 启动 + 变更时 + **每 2s 重发** | ≈227 B |
| `FRAME` | 2 | 每整帧 | `72 + 波束数×每波束字节数` = 54,728 B |
| `HEARTBEAT` | 3 | **每 1s**（设备未开采集时也发，用于判活） | 32 B |

**`CONFIG` 覆盖 39 个字段**，分 6 段：

| 段 | 代表字段 |
|---|---|
| 板卡 | 板卡类型 / IP / 激励电压 / 脉宽 / PRF / 滤波档位 / **采样点数 / 时基范围(ns)** / 采样起点 |
| 探头 | 探头名 / 阵元总数 / 阵元间距 / 中心频率 |
| 楔块 | 楔块名 / 角度 / 声速 / 第一阵元高度 / 主轴偏移 |
| 扫查 | 扫查模式 / 孔径 / 步进 / 波束数 / 成像高度 / **成像起始偏移** / 聚焦角深 / **试件声速** |
| 时基 | **采样率** / 采样率来源 / 采样位宽 / ADC 位深 |
| 位置 | 双轴编码器分辨率 / 极性 / 模式 |
| 尾部 | **`notes` 自由文本**（把设备端的"自我说明"随包发出） |

**帧包数据段**：`[波束][采样点]` 行优先，`61 × 896` 字节（uint8）。

## 六、当前问题详情

### 6.1 帧率异常（阻断项）

**现象**：心跳正常（1 条/秒，计数递增），但 10 秒内只有 1 帧。

**判断**：发送线程存活，问题在**攒帧——61 个波束凑不齐一帧**。

**已加入诊断**：设备端日志每 10 秒输出一行攒帧状态，形如：

```
攒帧 槽0=60/61 槽1=0/61 beamId范围=0..59 越界=0 重复=0 换帧=0
```

**三个候选原因**（诊断行可直接区分）：

| 诊断表现 | 原因 |
|---|---|
| `beamId范围` 不是 `0..60` | 波束编号基准不对（疑似从 1 开始），导致永远差一个波束 |
| `换帧` 计数持续增长、槽计数很小 | 一帧内 61 个波束的帧号不一致或帧间交错 |
| `重复` 计数增长 | 同一波束被重复上报 |

### 6.2 采样点数不一致

```
CONFIG 报告 sample_point_num = 1000   （板卡配置）
FRAME 实际 sample_count      = 896    （每波束字节数）
```

**相差 104 点（约 10%）**。`ReciveDataProcessManager` 中处理该场景的保护代码（`dataLength = pointNum - startIndex`）**当前处于注释状态**，需确认板卡是否按 1000 点发送、而上位机每包只取 896。

## 七、已知限制（设计上的取舍，非缺陷）

| 项 | 说明 |
|---|---|
| **设备无硬件时戳** | 全树确认无任何时钟字段。`device_timestamp_ns` 恒 0（表示"未知"），帧间时序只能用 `frame_seq` + 采集端收包时刻 |
| **采样率为反推值** | `fs = 10 MHz` 由 `采样点数 / 时基范围` 推导，标注为 `derived_unverified`，`calibrated` 状态位不置位。需用已知厚度试块实测验证 |
| **采样位宽 8 位** | 原始数据在设备内部即为 `byte`，非传输截断。是否可提升到 16 位需查设备底层库 |
| **`startNs` 不可信** | 既有代码缺陷：每次下发参数会累加楔块延迟（非幂等）。已如实标注 `trusted=0` |
| **编码器单位未定** | 字段值已发出，但单位方向（计数/毫米 还是 毫米/计数）待实测确认，故标注 `unknown` |
| **本轮只做线扫** | 扇扫 / TFM 的数据段结构不同，未纳入 |
